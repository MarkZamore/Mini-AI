# Контракт автономного model-worker v1

> Дополнение от 24.10.2026: исходный CPU-комплект v1 остаётся совместимым. Ниже отдельно описан manifest v2 для проверяемых локальных DLL и CUDA; это явное расширение контракта, а не исключение из проверки v1. Протокол генерации `enterpriseai.inference.v1` не меняется.

## Manifest v2: локальная CUDA и обработка доказательств

Manifest v2 также допускает один необязательный plain LoRA GGUF:

```json
"adapter": {
  "path": "adapters/selector-r8.gguf",
  "sha256": "<actual adapter SHA-256>",
  "baseWeightsSha256": "<exact weights.sha256>"
}
```

Это иллюстрация, не готовый manifest. Путь — один канонический файл
`adapters/[a-z0-9][a-z0-9._-]{0,127}.gguf` внутри model; он с тем же SHA обязан
входить в `files`. `baseWeightsSha256` обязан совпадать с SHA точных
инвентаризированных базовых весов. Java и worker проверяют эти связи, хеши и
GGUF-сигнатуры; неизвестные поля, другие пути и manifest v1 с адаптером
отклоняются. Состав DLL и требования CPU/CUDA не ослабляются.

Worker загружает адаптер после базовой модели и прикрепляет к context до
`ready`, с фиксированным scale 1 (встроенный GGUF alpha/rank применяет движок).
Только при наличии адаптера worker выполняет один внутренний valid-token decode
без чтения/публикации logits, синхронизируется, очищает всю KV/recurrent-память и
сбрасывает perf-счётчики. В закреплённой ревизии это инициирует резерв графа для
сконфигурированных `min(n_ctx,n_ubatch)` и `n_seq_max` с активным адаптером,
до проверки бюджета и `ready`. Это не прогон полного 16K-запроса, не доказательство
пригодности 16K-обучения и не универсальная гарантия отсутствия OOM. Действуют
прежние проверки памяти/отмены; без адаптера дополнительного decode нет.
Поддерживается обычный LoRA без DoRA/RSLora, новых токенов и дополнительных
полных модулей. Архитектуру и размеры матриц проверяет закреплённый движок;
факт загрузки не подтверждает смысловое качество. Память адаптера и графа
учитывается теми же проверками бюджета/резерва, без увеличения лимитов.
При завершении context освобождается перед адаптером, адаптер — перед моделью.
Без поля `adapter` поведение прежнего v2 сохраняется. Протокол generation
JSONL v1, отмена и ограничения вывода не изменяются; нет передачи пути адаптера
или переключения адаптеров через запрос пользователя.

`schemaVersion: 2` сохраняет обязательные поля v1 и добавляет `backend` и `dependencies`. Разрешён один `inference-worker.exe`. DLL допустимы только непосредственно в `model/runtime/`, каждая перечислена с SHA-256 одновременно в `dependencies` и `files`. Дополнительные EXE, подмена системных API/драйвера, неизвестные поля, выход из корня и непроверенные DLL отклоняются. Host проверяет PE-импорты EXE и каждой DLL по замкнутому списку хешированных зависимостей и явным системным API Windows. Дополнительные API sets v2 не разрешаются старым manifest v1.

```json
"backend": {
  "kind": "cuda",
  "device": 0,
  "gpuMemoryBudgetBytes": 8589934592,
  "reserveFreeGpuMemoryBytes": 3221225472
},
"dependencies": [
  {"path":"runtime/llama.dll","sha256":"<реальный SHA-256>"}
]
```

Пример неполон и не является готовым manifest. `kind` равен `cpu` или `cuda`; для CPU `device` и оба значения памяти равны нулю. Для CUDA бюджет положительный, резерв не меньше 512 MiB. Подготовленный профиль использует резерв 3 GiB для рабочего стола и Teams. До загрузки модели worker проверяет доступную память устройства относительно бюджета и резерва; после создания контекста проверяет их повторно. Это контроль допуска и фактического распределения при инициализации, а не аппаратная квота VRAM: другое приложение может изменить свободную память позднее. Лимит Job Object продолжает ограничивать commit процесса и не заменяет контроль GPU.

DLL загружаются после проверки полного inventory, по абсолютным путям. Поиск ограничен проверенной папкой runtime и System32, backend не ищется в PATH или рабочей папке. Драйвер `nvcuda.dll` поставляется Windows/NVIDIA отдельно и не может входить в model. Официальные CUDA DLL не являются частью обещания статической CRT исходного worker; необходимые Microsoft runtime DLL включаются в inventory. Требование устанавливать CUDA Toolkit, Java или Python у пользователя не вводится. Произвольный сетевой сервер не запускается.

Для генерации первый `hello` по-прежнему использует `enterpriseai.inference.v1`, затем следуют прежние frames и правила отмены. Другой backend не выбирается незаметно при недостатке памяти или отсутствии CUDA. CPU-режим — явно заданный профиль той же полной поставки.

Опциональный раздел `evidence` описывает `embedder:{path,sha256}`, опциональный `reranker:{path,sha256}`, `tokenizerDirectory` и `index:{path,sha256}`. Веса, индекс, его составляющие и все файлы токенизатора должны входить в `files`. Канонические `docs/db` этот протокол не меняет. Для отдельного процесса обработки доказательств host запускает тот же EXE с `--stdio`, но отправляет первым `hello` с `enterpriseai.evidence.v1`. Worker читает ровно этот frame до выбора обработчика; stdin следующих запросов не теряется. Сборка без evidence не сообщает фиктивную готовность, а возвращает ошибку. Незнакомые или отсутствующие конфигурации не подменяются произвольными результатами.

Исходники воспроизводимой подготовки: `src/model-worker`. Версия движка, release tag, контрольные суммы исходников и официальных DLL фиксируются там. Установка драйвера требует отдельного решения, если имеющийся драйвер несовместим; подготовка wrapper и распаковка app-local DLL не требуют UAC. Действия драйвера и Windows не объявляются доказанно свободными от записей. Process Monitor не входит в обязательные проверки по решению пользователя.

Эта спецификация дополняет `model/instructions.md`. Подготовка весов и worker выполняется отдельным конвейером подготовки; настоящий документ не является моделью и не разрешает работающему приложению скачивать или обучать её. Наличие схемы не подтверждает готовность модельного комплекта.

## Состав и проверка manifest

`model/worker.json` соответствует `worker-manifest.schema.json` (JSON Schema 2020-12). `engine` — имя движка, `revision` — его точная ревизия, отдельные обязательные поля. `architecture` равно `windows-x64`, `protocol` равно `enterpriseai.inference.v1`, `executable` равно `inference-worker.exe`.

Все пути относительны к фактической папке `model` рядом с EXE и используют `/`. В `files` перечислены **единственный EXE и все необходимые данные** (веса, токенизатор, конфигурация), включая `executable` и `weights.path`; SHA-256 каждой записи соответствует реальному файлу. `weights.sha256` и запись того же файла в `files` должны совпадать. Дубли путей с разным регистром или другим написанием запрещены. В manifest v1 любая DLL и любой дополнительный EXE в папке, включая вложенные папки, запрещены даже при наличии правильной контрольной суммы в `files`; v2 допускает только описанный выше hashed DLL inventory.

Папка `model` заменяется целиком при закрытом приложении; смешивать файлы разных комплектов нельзя. Отдельные комплектные варианты для слабых, средних и мощных устройств могут менять движок, ревизию, формат весов и проверенный профиль. Основной EXE приложения остаётся тем же. Суффикс `.gguf` не обязателен: worker проверяет фактический формат, архитектуру и совместимость файлов до `ready`, иначе отвечает `INCOMPATIBLE_MODEL`.

Структурная схема не заменяет проверки приложения: путь должен остаться внутри реального `model` после разрешения junction/symlink; запрещены Windows device names, traversal, ADS, отсутствующие и нечитаемые файлы. Проверяются все контрольные суммы до запуска. Реестр файлов не обеспечивает криптографическую аутентичность происхождения: совместимость и доверенное происхождение самого комплекта подтверждаются при подготовке.

`supportedIsa` означает **необходимые** наборы инструкций CPU, а не меню возможных backend. Например, `x86-64` и `avx2` требуют подтверждения обоих. Неизвестные названия и неподтверждённая поддержка отклоняются. Нельзя выводить AVX2 только из имени процессора. До окончательной проверки выбранного профиля приложение вправе отклонить его.

`minFreeMemoryBytes` — измеренный порог доступной физической памяти непосредственно перед запуском; `maxProcessMemoryBytes` — жёсткий лимит памяти worker в Job Object. Это разные величины; лимит worker должен быть меньше порога свободной памяти с документированным резервом ОС/приложения. `contextTokens` и `threads` задают проверенный профиль; приложение не уменьшает их или `precision` автоматически. Если доступных ресурсов недостаточно, запуск отклоняется. В manifest не допускаются абсолютные пути или неизвестные поля.

### Иллюстрация, не пригодная для запуска

Ниже **не** готовый `worker.json`: placeholders SHA-256 намеренно не соответствуют схеме. Значения памяти — гипотеза из инструкции, не результаты испытаний. Подготовитель заменяет их измеренными значениями и реальными хешами.

```json
{
  "schemaVersion": 1,
  "protocol": "enterpriseai.inference.v1",
  "executable": "inference-worker.exe",
  "engine": "llama.cpp",
  "revision": "<exact-tested-engine-commit>",
  "architecture": "windows-x64",
  "supportedIsa": ["x86-64"],
  "weights": {
    "path": "weights/universal-Q6_K.gguf",
    "sha256": "<actual-64-hex-SHA-256>"
  },
  "files": [
    {"path": "inference-worker.exe", "sha256": "<actual-64-hex-SHA-256>"},
    {"path": "weights/universal-Q6_K.gguf", "sha256": "<actual-64-hex-SHA-256>"}
  ],
  "precision": "Q6_K",
  "contextTokens": 8192,
  "threads": 8,
  "minFreeMemoryBytes": 27917287424,
  "maxProcessMemoryBytes": 25769803776
}
```

Worker manifest v1 обязан быть статически связан, включая Microsoft CRT (`/MT`); папки `model/native` с библиотеками нет. Перед запуском приложение проверяет x64 PE, обычные и отложенные импорты. В v1 разрешены только библиотеки базовой Windows 11 и системные API sets; VC Redistributable, OpenMP, CUDA, SYCL и сторонние зависимости отклоняются с `MODEL_PACKAGE_NOT_SELF_CONTAINED`. Проверка PE не доказывает отсутствие динамических загрузок по `LoadLibrary`. Лицензии и отчёт подготовки поставляются вместе с комплектом как обычные данные.

## Запуск и ограничения worker

Приложение запускает проверенный `model/inference-worker.exe --stdio` напрямую, без командной оболочки, в скрытом процессе. stdin/stdout/stderr — анонимные каналы. Worker закрепляется в Windows Job Object до разрешения работы; закрытие приложения завершает job. Дополнительные handles не наследуются.

Worker загружает только свой проверенный комплект, открывает веса read-only и не ищет компоненты в текущей папке, PATH или сети. Исходный статический worker v1 не создаёт файлы, кеши, логи, настройки реестра, сеансы, дампы или распакованные DLL; это обещание не переносится автоматически на драйвер и сторонние библиотеки v2. Не допускаются сервер, сокеты, downloader или сохранение prompt cache. Сообщения stderr сохраняются приложением только в ограниченном RAM-буфере. Системные действия Windows/защитного ПО классифицируются отдельно при испытаниях.

## JSON Lines

Один UTF-8 JSON-объект на строку, без BOM. Переводы строки внутри текстов JSON-escaped. stdout содержит исключительно протокол; баннеры и диагностика туда не печатаются. Максимальная длина **входной и выходной строки — 8 MiB байт**, до декодирования/разбора. Лимит контролируется потоковым чтением, а не после неограниченного `readLine`. Допускается CRLF или LF между frames. Дубли полей JSON, malformed UTF-8, неизвестные типы/лишние поля и сообщения неправильного направления являются ошибками протокола.

`worker-protocol.schema.json` проверяет отдельный frame. Направление, порядок, общий размер, лимит контекста и привязка ID проверяются отдельно:

| Направление | Тип | Значение |
|---|---|---|
| Приложение → worker | `hello` | Первое сообщение, версия протокола |
| Worker → приложение | `ready` | Подтверждение совместимого протокола и готовности |
| Приложение → worker | `generate` | `requestId`, массив `messages`, положительный `maxTokens` |
| Worker → приложение | `token` | Текстовый фрагмент активного `requestId` |
| Worker → приложение | `done` | Успешное завершение активного запроса |
| Приложение → worker | `cancel` | Отмена активного запроса |
| Worker → приложение | `cancelled` | Завершение отмены |
| Worker → приложение | `error` | Ошибка; активный запрос указан через `requestId` |

Пример штатного обмена:

```jsonl
{"type":"hello","protocol":"enterpriseai.inference.v1"}
{"type":"ready","protocol":"enterpriseai.inference.v1"}
{"type":"generate","requestId":"r-1","messages":[{"role":"system","content":"Отвечайте только по представленным источникам."},{"role":"user","content":"Запрос и выбранные приложением фрагменты."}],"maxTokens":1024}
{"type":"token","requestId":"r-1","text":"Подтверждённый ответ [fragment-id]."}
{"type":"done","requestId":"r-1"}
```

`requestId` непустой, не более 128 символов; приложение создаёт уникальный ID. Роли ограничены `system`, `user`, `assistant`. `maxTokens` не превышает `contextTokens`; движок отдельно проверяет, что токенизированный prompt вместе с разрешённым ответом помещается в контекст. При превышении отвечает `CONTEXT_TOO_LARGE`, а не обрезает текст молча.

Одновременно активен один запрос. `generate` принимается только после `ready`. Каждый запрос завершает ровно один terminal frame: `done`, `cancelled` или `error`. После него `token` для этого ID запрещён. Неизвестный/устаревший ID не может дописывать историю другого запроса. Повторное завершение или неожиданный frame приводит к остановке worker с ошибкой протокола.

Для manifest v2 приложение может сохранить один готовый generation worker после `done`. Повторное использование требует прежних real-path model и полного manifest, живого процесса, отсутствия queued frames и успешного завершения предыдущего запроса. Полный SHA/PE audit выполняется перед первым запуском; native удерживает manifest и все проверенные assets открытыми с запретом записи/удаления на всё время жизни процесса. Каждый `generate` полностью очищает KV/память предыдущего запроса: история передаётся только явно в `messages`. При отмене, ошибке, закрытии или изменении описания комплекта transport завершается; следующий запрос проходит полную проверку и запускает новый worker. Manifest v1 сохраняет запуск отдельного процесса для каждого запроса. Wire JSONL v1 не меняется.

`cancel` обрабатывается параллельно вычислению и прекращает генерацию. UI сразу показывает отмену. Если worker не отвечает в течение двух секунд, приложение завершает процесс и job; следующий запрос требует нового worker. При EOF stdin worker освобождает память и завершает процесс. Закрытие stdout/stderr, авария и нехватка памяти не должны завершать окно EnterpriseAI.

```jsonl
{"type":"cancel","requestId":"r-1"}
{"type":"cancelled","requestId":"r-1"}
{"type":"error","requestId":"r-2","code":"OUT_OF_MEMORY","message":"Недостаточно памяти для генерации."}
```

`error` без `requestId` допустим при handshake/startup/process failure. Ошибка активной генерации обязана содержать её ID. Коды ошибок — прописные ASCII слова с `_`; основные коды: `OUT_OF_MEMORY`, `CONTEXT_TOO_LARGE`, `INCOMPATIBLE_MODEL`, `INVALID_REQUEST`, `INTERNAL_ERROR`. Ошибка — диагностическое сообщение, не команда приложения.

## Данные и цитаты

Messages содержат только запрос, RAM-историю и выбранные приложением исходные фрагменты со ссылками/предупреждениями. Они не задают пути произвольного чтения и не запускают инструменты. Документные инструкции остаются данными. Модель не получает доступ к shell, SQL, реестру, сети, обучению или папкам источников.

Приложение принимает цитаты только для реально переданных фрагментов и версий. Worker не вправе создавать новый source ID или объявлять непроверенный OCR вручную проверенным. Реальная RAG-оценка готового комплекта обязательна; файловые и реестровые операции будущим конвейером не подтверждаются. Mock worker проверяет только транспорт.
