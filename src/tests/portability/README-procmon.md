# Наблюдение Process Monitor на ноутбуке разработчика

Это отдельный **наблюдатель**, а не компонент поставки. Подготовка скрипта и скачивание утилиты не являются проведённой трассировкой. На этапе подготовки Procmon не запускался, UAC не вызывался; процесс агента не имеет административного токена.

После подготовки проведён локальный запуск `0ad496a293ae43d7b5c8b163b1ed2456` с пользовательским UAC и сохранённой конфигурацией. Итог конкретных девяти сценариев: [local-scoped-summary.json](../../build/test-results/procmon/0ad496a293ae43d7b5c8b163b1ed2456/local-scoped-summary.json). Ниже описан воспроизводимый workflow; историческое состояние подготовки не заменяет этот фактический отчёт.

## Происхождение, лицензия и CLI

Microsoft [описывает Process Monitor](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon) как наблюдатель файловой системы, реестра и процессов с исходными стеками. Скачан официальный `https://download.sysinternals.com/files/ProcessMonitor.zip` версии 4.11 в `src/build/tools/procmon`. `verification.json` фиксирует SHA-256 и валидные Microsoft Authenticode-подписи всех трёх EXE; перед запуском `Procmon64.exe` подпись проверяется повторно.

В `Eula.txt` — условия Sysinternals, а не open-source лицензия. Утилита допускает использование на своих устройствах, но не включается в поставку EnterpriseAI и не публикуется для копирования другими. Применение `/AcceptEula` означает принятие условий; требуется явный флаг `-AcceptSysinternalsLicense`. Трасса может содержать приватные имена, пути и данные реестра; она остаётся внутри `src/build`.

[Microsoft документирует запуск и остановку через CLI](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/troubleshoot-apps-start-failure-use-process-monitor). Дополнительные ключи сверены со строками Help/Command Line Options в подписанном `Procmon64.exe`; при первом разрешённом запуске следует проверить текущий Help. Используются `/BackingFile`, `/Quiet`, `/Minimized`, `/NoFilter`, `/LoadConfig`, `/WaitForIdle`, `/Runtime`, `/Terminate`, `/OpenLog`, `/NoConnect`, `/SaveAs`, `/SaveAs1`. `/SaveApplyFilter`, boot logging, `/PagingFile`, RPC/PsExec и symbol-server download не используются. PML хранит полную трассу, CSV упрощает сортировку, XML `/SaveAs1` сохраняет сырые стеки без сетевого разрешения символов.

## Подготовка без повышения прав

Из PowerShell 7 обычного пользователя, находясь в `src`, выполнить:

```powershell
./tests/portability/procmon_audit.ps1 -Mode Prepare
```

Скрипт создаёт новый `src/build/test-results/procmon/<id>`; сохраняет хеши согласованного EXE и исходного индекса, список сценариев и копии повреждаемых тестовых данных. Оригинал индекса **не** используется через hardlink/junction в повреждаемых fixtures. Ничего не запускается. Конкретная папка будет напечатана; существующее свидетельство не перезаписывается.

Исходные документы/индекс/модель не редактируются. Проверки `status`, `search`, `graph`, `ui-smoke` читают существующий набор рядом с реальным EXE. Отдельные копии EXE/DLL проверяют отсутствие всех папок, повреждённый SQLite и отсутствие model. Если уже собран локальный CrashProbe, в план входят JNI fatal и пойманный Java OOM. Это не тест аварии реального inference-worker.

## Стандартный Windows UAC для наблюдателя

Перед Capture нужен **проверенный `.PMC`**, сохранённый через интерфейс Procmon в `src/build/tools/procmon/all-events.pmc`. Пользователь уже разрешил необходимые инструменты для этих испытаний; отдельное подтверждение лицензии или установки в чате не требуется. Для подготовки конфигурации и трассировки нужен стандартный Windows UAC с действующими административными данными. Пароль вводится исключительно в системном окне, не в чате. Не отключать UAC, не менять policy, не создавать службу вручную и не обходить защиту. Procmon сам загружает собственный подписанный kernel driver и может записывать свои настройки/лицензию — эти действия относятся к наблюдателю.

В конфигурации проверить: включены File System, Registry, Process/Thread и Network (для контроля отсутствия запросов); Filter очищен; **Drop Filtered Events выключен**; thread profiling и boot logging выключены; пути/PID не ограничивают capture. Не настраивать загрузку символов из интернета. Сохранить `.PMC` и закрыть подготовительный экземпляр Procmon. `/NoFilter` дополнительно убирает фильтры при записи; он не заменяет проверку классов и полноты.

Подготовка конфигурации через GUI и последующая Capture — отдельные запуски наблюдателя; Windows может показать UAC для каждого. Не обещается одно системное окно для всей процедуры. GUI-настройка сейчас выполняется пользователем: native UI automation в текущей среде недоступна. Агент не вводит и не запрашивает административный пароль.

Затем **неповышенный** координатор запускает:

```powershell
./tests/portability/procmon_audit.ps1 -Mode Capture `
  -RunDirectory '<созданная папка src/build/test-results/procmon/id>' `
  -Configuration './build/tools/procmon/all-events.pmc' `
  -ConfigurationVerified -AcceptSysinternalsLicense
```

Координатор проверяет отсутствие admin-токена и запускает отдельный observer через `Start-Process -Verb RunAs`; это стандартный Windows UAC, не автоматическое одобрение. Все **EnterpriseAI/CrashProbe процессы запускает исходный обычный координатор** после `WaitForIdle`, напрямую, без shell, с анонимными stdout/stderr-каналами. Наблюдатель никогда не запускает приложение с правами администратора.

Существующая Procmon-трасса не закрывается и не заменяется: скрипт отказывается работать, если экземпляр уже активен. Собственная запись ограничена `/Runtime 150`; при штатном завершении отправляется `/Terminate` только после проверки единственного собственного PID. Если владение неоднозначно, чужой экземпляр не закрывается. Все PML/CSV/XML, сообщения observer и результаты процессов находятся в указанной `src/build`-папке.

## Разбор и граница результата

`classification.json` — **предварительная классификация**, не сертификат. CSV не содержит полного стека; для каждого спорного события открыть PML/Event Properties/Stack или `trace-stacks.xml`. Проверять image path, parent, время создания и завершения PID: PID может использоваться повторно. Код системной DLL внутри PID приложения нельзя автоматически объявлять независимым действием Windows.

Категории: приложение и загруженные DLL; контролируемые дети, включая worker; Windows/защитное ПО/драйверы; Windows Open With и выбранная внешняя программа; наблюдатель/driver/координатор; несвязанные или пока не атрибутированные процессы. Неизвестный ребёнок приложения требует разбора. Реальный worker пока отсутствует; это явно непроверенный сценарий.

`WriteFile`, resize, rename/delete, изменение атрибутов/безопасности и записи реестра — кандидаты нарушения. **ACCESS DENIED при попытке записи также провал.** `CreateFile` с read access и `Disposition: Open` является открытием для чтения; `Generic Write`, append/delete или создающая/перезаписывающая disposition — попыткой изменения. `Maximum Allowed`, mapping/FSCTL/DeviceIoControl и незнакомые операции разбираются по сырой трассе. Анонимные stdout/stderr/worker pipe — IPC в памяти; исключение не распространяется без проверки на произвольные named pipes.

При независимом действии ОС, защитного ПО или внешнего просмотрщика сохранить конкретные строки, stack и обоснование. Не делать глобальный whitelist системных модулей. Сначала удалить все неразобранные кандидаты доказательным разбором; только затем фиксировать результаты **конкретного** комплекта/Windows/сценария. Полный `docs/db/model` сверить через `audit_data.py`; один хеш индекса недостаточен.

Отдельно обычный пользователь выполняет интерактивный граф: pan/zoom/drag/нажатие, разделитель, повторную отправку и закрытие. Для ручной трассы заранее запустить observer и обычное приложение, записать его PID/временной интервал и действия; не заменять это `ui-smoke`. Открытие оригинала внешней программой — отдельный явно согласованный сценарий: программа может писать кеши и изменять оригинал. Не использовать его без сохранённой копии документа, если нужен контроль неизменности оригиналов.

Этот аудит на ноутбуке не доказывает работу на чистой Windows без dev tools и не обещает нулевые изменения всей ОС. Политики crash dump Windows не меняются и не выдаются за гарантию приложения. Первый запуск, отмена/зависание/OOM реального worker и окончательная модель проверяются после подготовки комплекта на другой машине.
